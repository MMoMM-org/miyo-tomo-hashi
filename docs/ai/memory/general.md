# General Memory

<!-- 2026-09-03 -->
- **A test or guard whose NAME promises more than its assertions deliver is a silent coverage hole — re-read the body of any test whose name claims "re-run", "idempotent", "byte-identical" or "invariant".** `editFrontmatter.test.ts` carried a test named *"re-running after a successful set → skipped-already"* that swapped `expected` to the post-apply state before running — so it asserted that a set to an already-correct value is a no-op, and never re-ran anything. A genuine re-run of the same wire action fails, for both `set` and `remove`, and nothing covered that. Found by reading the handler line by line to answer a Tomo question, not by any failing test. Tomo hit the same class twice the same day in their own repo: a report-language fix that landed at three call sites and missed a fourth (no test reads the rendered report as prose; a person did), and a guard named `..._body_resident_output_byte_identical_con7` that actually asserted "exactly one changed line in the whole report" — a proxy that held only while one fix existed.
  - **Why:** the name is what a reader greps for and what a reviewer trusts; a green suite plus a reassuring name reads as coverage. The gap survives precisely because nobody re-reads a test that appears to already cover the case.
  - **How to apply:** when a test name makes a *behavioural* claim, check that the arrange step does not quietly satisfy the postcondition before the act. Concretely: if the name says "re-run", the same action object must be executed twice; if it says "invariant", assert the invariant, not a proxy that happens to correlate today. Prove a guard bites by breaking the thing on purpose (inject `sorted()`, change the output) rather than asserting the suite still passes.

- **Verify the version number a claim travels with, not just the claim.** In the 2026-09-01 `edit_frontmatter` handoff we told Tomo the kind was "live in 0.23.0". It is not: the kind landed in **0.22.0**, the pre-check in 0.23.0, and the `expected` / `expected_absent` split in **0.23.1**. The number survived a full round trip — we wrote it, Tomo adopted it into spec 032, quoted it back, and we verified four separate schema claims in that same message without ever checking the version attached to them. Kokoro caught it by auditing every version claim against `CHANGELOG.md`.
  - **Why:** version numbers ride along with technical claims and inherit their credibility. A carefully verified claim makes the unverified number beside it look verified too — and in a handoff the number is the part that becomes a downstream compatibility floor, outliving the discussion that produced it.
  - **How to apply:** any handoff, ADR or doc that names a Hashi version must have that version read out of `CHANGELOG.md`, not recalled. Cheap check: `rg -n "^## \[0\." -A 25 CHANGELOG.md` and find the actual feature line. State *which* change the version refers to (the kind landing vs. a later refinement) — "shipped in X" is ambiguous when a kind lands in one release and its schema changes in another.

<!-- 2026-07-27 -->
- **When labeling N same-kind UI controls by a vault-relative path's basename, count basenames first — only show the short label where it's actually unique.** Spec-006 T4.2's multi-source "Open Instruction Fixer" buttons initially labeled every button with its basename and put the full path only on the `title` tooltip. Vaults commonly repeat filenames across folders (`100 Inbox/x.json` vs `200 Archive/x.json`), so two failing sources with the same basename rendered two buttons with IDENTICAL visible text — distinguishable only by hovering — on the screen whose whole job is "pick the one you want." Caught by code-quality review.
  - **Why:** a `title` attribute is not discoverable without hovering, so it cannot carry the disambiguating information a sighted, non-hovering user needs to make the choice the UI exists to offer.
  - **How to apply:** build a `Map<basename, count>` over the candidate set; a control whose basename count is 1 keeps the short label, one whose count is >1 falls back to the full (disambiguating) path. `title` still carries the full path either way. See `fixerButtonLabel`/`countBasenames` in `src/ui/modalContent/summaryView.ts`. Applies to any list keyed by vault-relative path where entries could come from different folders — picker lists, multi-source run summaries, etc.

<!-- 2026-04-28 -->
- **`tsconfig.json` `include` must list `test/**/*.ts` from day 1.**
  Tests outside `include` cause LSP "Cannot find module" diagnostics on every new test file — vitest resolves fine at runtime, but the editor experience degrades and `tsc -noEmit` skips type-checking the test surface entirely. Hashi hit this 3× during phase-1 implementation (commits `09b27bd`, `7734334`, `5402455`) before the include was widened in `4d039f2`. Widening immediately surfaced one real `noUncheckedIndexedAccess` violation that vitest had been masking.
  - **Why:** LSP and `tsc` use `include` to bound their world; vitest uses its own resolver. Without alignment, type errors in tests escape both the IDE and the build.
  - **How to apply:** for any new TS project (Hashi-style or another MiYo TS plugin), the very first `tsconfig.json` should ship with `"include": ["src/**/*.ts", "test/**/*.ts"]` — not retrofitted after the first wave of test files lands. Tests should explicitly import from `vitest` (no globals) so they compose with the same `strict: true` / `noUncheckedIndexedAccess: true` profile as `src/`.
